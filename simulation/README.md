# spot_pico simulation — MuJoCo residual-gait training

MuJoCo physics + Gymnasium + Stable-Baselines3 PPO for training a **residual walking policy**
on the `spot_pico` quadruped. The baseline is the ESP32 firmware gait ported to NumPy; the
policy learns only small per-foot corrections on top (`residual_pure`, à la spot_mini_mini D2 /
the Hexapod project). A zero action reproduces the firmware gait, so training starts from a
working gait and only learns stabilization.

Managed with **uv** (Python ≥ 3.13).

```bash
uv sync
uv run python gen_protos.py   # the robot's protocol classes in src/proto/ (gitignored); needed by the Robot API, record.py and the tests
```

`gen_protos.py` compiles `platform_shared/filesystem.proto`, `api.proto` and `message.proto`, the same files the firmware and the web app use.

## Architecture

```
command [vx, vy, yaw]  ->  analytic_gait_action  ->  firmware gait (phase clock, trot
                                                     offsets, stance + 12-pt Bezier swing)
   -> Cartesian foot targets (base frame)  + policy residual (12-D, ±15 mm)
   -> analytic IK  ->  12 joint angles  ->  MuJoCo position actuators (100 Hz control)
```

- `src/robot/firmware_gait.py` - NumPy port of `esp32/include/motion_states/walk_state.h` + spot_pico analytic IK
  (verified to 0.0 mm against MuJoCo forward kinematics) + command-to-gait map.
- `src/robot/stand_compensation.py` - port of the stand state's IMU levelling (`motion_states/state.h`), used by the
  simulation backend in STAND; `src/sim/slope_stand.py` stands the robot on a tilted floor with it.
- `src/sim/mj_runtime.py` — MuJoCo runtime wrapper (load model, IK→ctrl, IMU/contacts).
- `src/sim/domain_rand.py` — per-episode/step domain randomization for sim-to-real.
- `src/sim/terrain.py` - per-episode heightfield ground for `scene_terrain.xml`: random bumps, a slope or stairs.
- `src/sim/stages.py` - the terrain and payload stages and the success-driven schedule that moves through them.
- `src/envs/quadruped_mj_env.py` — Gymnasium env; 12-D residual action, 38-D hardware-only
  observation (gravity-in-body, gyro, rpy, prev joint cmd, gait phase, command, prev action),
  ANYmal-style exponential velocity/yaw tracking reward (weights 3.0 and 1.0) minus penalties on
  tilt, base height, vertical speed, actuator force, power, action rate, foot slip, roll/pitch rate
  and residual magnitude; an episode ends when the body tips over or drops below 3 cm.
- `src/resources/spot_pico/` - MJCF `scene.xml` and `scene_terrain.xml`, `spot_pico.urdf`, meshes,
  `linkage.py` (four-bar tibia map, deploy-time only), tuned `gait_coef.json`.
- `src/resources/spot_micro/`, `src/resources/yertle/` - `scene.xml` for the other two robots, generated by `generate_scenes.py` for the web app's simulation. The Gymnasium env, `train_mj.py` and `replay_gait.py` use only spot_pico.
- `src/leika/` - one `Robot` for the simulation and the real robot (see Robot API): `robot.py`, `motions.py`, `speed_model.py`, and `backends/` (`sim.py`, `real.py`).
- `src/proto/` - the generated protocol classes (not committed).
- `src/sim/recording.py`, `src/sim/telemetry_stats.py` - the `.leika` telemetry file and the statistics the report prints.

The spot_pico scene was derived from the `spot_pico_description` package, which is neither a dependency nor part of this repository; the files in `src/resources/spot_pico/` are what the code loads. The four-bar tibia linkage (`linkage.py`)
is only needed when deploying to real servos; in sim the URDF tibia joint is actuated directly.

## Commands

```bash
uv run python -m src.robot.firmware_gait   # IK/FK self-test + stance angles
uv run python replay_gait.py --headless    # validate the zero-residual gait (all directions)
uv run python replay_gait.py --vx 0.05     # watch the baseline gait in the viewer

uv run python optimize_gait.py --iters 30  # calibrate command->gait map -> gait_coef.json

uv run python train_mj.py --smoke                                   # pipeline sanity run
uv run python train_mj.py --randomize --zero-final --init-std 0.3 \
    --curriculum --resample-steps 300 --timesteps 5_000_000 --num-envs 16

uv run python eval_policy.py runs/residual_pure_dr --vx 0.05        # watch a trained policy (--headless prints tracking metrics)
uv run python visionary_demo.py [address]                           # Robot API demo; an address drives the real robot
uv run python record.py --robot 192.168.1.39 --seconds 60           # record the real robot's telemetry (--out sets the file; --robot COM10 over USB)
uv run python report_recording.py recording.leika [--still]         # its timing and IMU noise vs domain_rand.py
uv run python calibrate_compass.py recording.leika [--write <address>]  # fit the compass's hard-iron offset, optionally store it
uv run python virtual_robot.py --port 8765                          # a robot on this computer, from the firmware's C++
uv run python release_smoke.py 192.168.1.39                         # the check before a release; exits non-zero on a breach

uv run python generate_scenes.py          # regenerate the spot_micro and yertle scenes from app/static
uv run python export_gait_trace.py        # golden gait trace for the web app's TypeScript port (app/tests/fixtures)
uv run python fit_pico_joint_map.py       # fit the Pico's firmware-to-MJCF joint map for the web app (app/src/lib/simulation/robots.ts)
uv run python check_animation.py          # play the built-in clips on the Pico from the firmware's animation trace: clamps, servo speed, knocks, tips, falls
uv run python check_stand_level.py        # does the stand's IMU levelling reduce the tilt on a slope, for either +z side
uv run python check_rise.py               # does the stand's IMU levelling tip the body on the rise from REST

uv run pytest -q                                                    # regression tests
```

Uneven ground: pass `--terrain 0.008` to `train_mj.py` to train on the heightfield scene
(`scene_terrain.xml`) with per-episode random bumps up to the given height in metres. The policy
is blind (IMU only, no exteroception), so terrain only enters through proprioception.

Stages: pass `--stages` instead to move through the terrain and payload stages of `src/sim/stages.py`: flat ground, then a payload of up to 0.15 kg on the base with an off-centre centre of mass, bumps, slopes up to 10 degrees and stairs with risers up to 10 mm.
An episode succeeds when the robot does not fall and tracks the commanded velocity well on average; the stage advances when 80 % of the last 50 episodes at it succeed, and falls back below 40 %, never below the first stage.
TensorBoard shows the stage as `curriculum/stage`.

TensorBoard: `uv run tensorboard --logdir runs`. Watch `terms/r_vel` (tracking) rise and
`terms/p_res` (residual magnitude) stay small — the policy should stabilize, not replace, the gait.

## Robot API

`Robot("simulation")` and `Robot("<robot address>")` expose the same calls, so a script written against the simulation runs on the robot by changing its target.
The target can also be the board's native USB port (`Robot("COM10")`, `Robot("/dev/ttyACM0")`), which carries the same protocol as WiFi, see [the serial link](../docs/serial.md); the robot's log lines from that port go to the `leika.robot_log` logger.
Velocities are REP-103 (forward, left, counter-clockwise) in m/s and rad/s, and angles are in degrees.

```python
from src.leika import Robot

with Robot("simulation") as robot:   # or Robot("192.168.1.39")
    robot.stand()
    robot.move_forward(0.2)
    robot.rotate(90)
    print(robot.state())
```

- `stand`, `rest`, `deactivate` and `set_gait` set the mode, `set_velocity` and `stop` drive, and `move_forward`, `move_sideways` and `rotate` move a distance or an angle.
- `state`, `calibrate` and `max_velocity` read from the robot.
- `odometry` reads the robot's dead reckoning since the last `reset_odometry` or deactivation (metres, yaw in degrees), and `reset_odometry` starts it afresh.
  It counts the steps the gait commanded: the simulation covers about 11 to 15 % more than it reports (`tests/test_odometry.py`), and the real robot's servos shorten its steps, so calibrate it against a tape measure.
- `goal_move` has the robot walk a distance or turn an angle itself, on its odometry, and returns once it reports the target reached (`GoalCancelled` or `RobotTimeout` otherwise); a WiFi stall cannot cut it short.
  `move_forward` and `move_sideways` are goal moves on a robot that takes them, and `rotate` turns by a goal and then closes the rest on the measured yaw.
  The simulation runs the firmware's goal controller on its odometry, so it lands where the robot would by that odometry: about 8 % long on a distance and 15 % on a turn by MuJoCo's base (`tests/test_goal_moves.py`).
- Leaving the `with` block, on an exception or Ctrl-C included, stops the robot and lets it rest.
  A robot the user deactivated stays deactivated, and the robot never deactivates on its own.
- The real robot is driven over its WebSocket (`ws://<host>/api/ws`).
  While the velocity is not zero, the input is re-sent every 100 ms, inside the firmware's 500 ms dead-man stop.
- Failures raise `RobotError`, `RobotTimeout`, `RobotDisconnected` or `UnknownVariant`.

## Recording telemetry

The firmware streams every control tick to subscribers: its timing, the IMU sample and the servo command.
`record.py` writes that stream to a `.leika` file and reconnects after a dropped link, marking the gap.
Three seconds without a frame count as a lost link.
`report_recording.py` prints the recording's latencies and IMU noise beside the ranges `src/sim/domain_rand.py` assumes.
Pass `--still` for a robot that stood still throughout, so the gyro mean is its bias and the spread its noise.
The app's System Metrics page records the same `.leika` file, for download, and shows the same summary when the recording stops.

`calibrate_compass.py` fits the compass's hard-iron offset to a recording made while the robot is turned slowly through every orientation (`src/sim/compass_fit.py`).
It undoes the mounting and the calibration the recording's header holds, fits a sphere to the raw readings, and refuses a recording that does not cover enough directions or whose field is not Earth's (25-65 uT).
With `--write <address>` it stores the offset in the robot's peripheral settings, keeping the rest.

## Virtual robot

`virtual_robot.py` builds `esp32/test/host/virtual_robot.cpp` from the firmware's own code and serves it on `ws://localhost:<port>/api/ws`, so the app and the Robot API drive it as they drive a robot.
It runs `MotionService` every 10 ms, with its gaits and its dead-man stop, the `ServoController` writing to a fake I2C bus, and the socket's decoder, subscriptions and telemetry.
It answers the features (the variant, the firmware's name and version, and the SHA-256 of the program as its ELF hash) and the servo settings, and refuses every other request with status 400.
The IMU reads level and still.

It needs a C++20 compiler (`$CXX`, or `g++`; on Windows MSYS2's UCRT64 `g++`) and the firmware's nanopb headers:

```bash
uv run python ../esp32/scripts/compile_protos.py
uv run python virtual_robot.py --port 8765 [--variant SPOTMICRO_ESP32_MINI]
```

It builds on every start; `--build <path>` builds once and `--binary <path>` runs that build.
To drive it from the app, run `pnpm dev` in `app/` and set the address to `localhost:8765` on the start page or on `/connection`.
From Python, `Robot("localhost:8765")` connects to it.

It does not cover WiFi, the web server, the I2C bus's timing, the sensors or FreeRTOS scheduling: the period it reports is this computer's, not the ESP32's.
The program speaks to the Python wrapper over stdin and stdout; `tests/test_virtual_robot.py` stands it up, walks it and checks its dead-man stop.

## Release smoke check

`release_smoke.py <address>` checks a robot before a release: it reads the features and the ELF hash, stands, walks two seconds in each gait, plays `wave` where the firmware has animations (it skips this when the protocol has none or the robot refuses), and records at least 500 ticks of telemetry.
It then deactivates the robot and exits 1 when a tick overran the 10 ms period more often than `--max-overruns` allows (default 5), a servo write failed, a joint was written to a PWM limit, an angle was not finite, the dead-man stop fired, or the legs did not swing while walking.
It exits 2 when the robot cannot be reached or driven.
The robot walks during the check, so give it room.
CI runs it against the virtual robot.
